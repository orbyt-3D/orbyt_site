Performance and memory

How orbyt keeps frames fast and GPU memory in check, and the settings you can tune.

Preview. The orbyt package is in active development. This page describes the 0.9.x API it is being built to; names may still change before 1.0.

What makes a frame expensive

  • Draw calls. Each separately drawn mesh costs CPU time. orbyt merges static parts that share a material into one draw.
  • Pixels. Cost grows with the number of rendered pixels. Resolution follows the screen and is capped by a pixel budget.
  • Shadows. Static scenes draw the shadow map once instead of every frame.
  • Post effects. Bloom runs at reduced resolution and can be switched off.

Adaptive quality

Flare watches frame time. If it stays above about 22 ms (below roughly 45 fps), resolution steps down in small increments, and bloom turns off as a last resort. The live scenes on this site use the same logic; open the showcase to see fps and draw calls as you orbit.

Memory budget

memoryBudgetMiB caps textures and geometry. When a model would exceed it, orbyt downsizes the largest textures first and logs what it changed.

new Flare(canvas, parts, { memoryBudgetMiB: 256, pixelRatio: 1 });

Tips

  • Share materials between parts that look the same: they merge into fewer draws.
  • Prefer KTX2/Basis textures for big models; they stay compressed on the GPU.
  • Keep moving parts few and separate; everything static can be merged.
  • Stop rendering when the canvas is off screen (an IntersectionObserver is enough).
  • Respect prefers-reduced-motion by pausing camera motion.
