Performance and memory

How orbyt keeps frames fast and GPU memory in check, and the settings you can tune.

0.9.2 preview. The engine is built and tested; publishing to npm is coming soon, so the install line below will work once the package is live. Names may still change before 1.0.

What makes a frame expensive

  • Draw calls. Each separately drawn mesh costs CPU time. Merge static meshes that share a material.
  • Pixels. Cost grows with the number of rendered pixels. Lower pixelRatio on large or slow screens.
  • Shadows. Pass a smaller shadow-map size, or shadows: false for scenes that don't need them.
  • Post effects. bloom: false or hdr: false skip the post-processing passes.
new Flare(canvas, parts, { pixelRatio: 1, samples: 2, shadows: 1024, bloom: false });

How this site stays smooth

The 3D on orbyt3d.space merges static meshes per material (about 130 draw calls for the whole launch site), draws its shadow map once, and steps resolution down if frames run slower than about 45 fps, turning bloom off as a last resort. Open the showcase to watch fps and draw calls as you orbit.

Memory in the MCP server

orbyt-mcp --memory <MiB> sets one budget for the headless renderer: the browser heap, the largest frame (256 MiB allows about 4 megapixels; larger requests are downscaled and the reply says so) and the largest model or HDRI file it will load (half the budget).

Tips

  • Share materials between parts that look the same: they merge into fewer draws.
  • Prefer KTX2/Basis textures for big models; they stay compressed on the GPU.
  • Keep moving parts few and separate; everything static can be merged.
  • Stop rendering when the canvas is off screen (an IntersectionObserver is enough).
  • Respect prefers-reduced-motion by pausing camera motion.
